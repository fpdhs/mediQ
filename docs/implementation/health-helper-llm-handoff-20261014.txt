1. 사용자 목표와 합의 사항

- 프로젝트: 하이패스 Platform. 학교 발표용 MVP/PoC, 합성 환자·가상 병원 데이터만 사용한다.
- 기존 구축 중인 한국어 번역 RAG를 이어서 개선하고 Azure 환자웹 건강도우미에 연결한다.
- 별도 출처 이용권리·번역 대조·적격 임상·편집 검토 담당자 배정 작업은 사용자 요청으로 제외했다. 별도 검토자를 다시 요구하지 않는다.
- 사용자 요청의 번역 후보 전체 PASS는 학교 데모 검색 코퍼스 채택 상태다. 콘텐츠 QA HOLD가 임상 승인 PASS로 바뀐 것은 아니다.
- 이전에 지정한 검토자 김범희/admin은 이후 별도 검토자 없이 진행한다는 요청으로 대체됐다. 새로운 인적 승인 절차를 임의로 추가하지 않는다.
- 현재 최우선 불만: 답변 품질과 QA HOLD 같은 내부 용어의 환자 화면 노출.
- QA HOLD 문구 노출 수정은 Azure에 반영 완료했다. 전체 답변 품질과 모델 안정성은 아직 개선할 부분이 있다.
- 사용자는 실제 Microsoft 환자 로그인은 나중에 진행한다고 명시했다. 로그인 검증을 완료했다고 주장하지 않는다. 비밀번호를 채팅에 요구하지 않는다.
- 번역문은 검색 근거로 사용한다. 모델 fine-tuning을 수행한 시스템이라고 설명하지 않는다.

주요 응답 상태:
- GENERATED: 실제 모델 문장 선택과 서버 검증 통과. 자유로운 요약 생성이 아니다.
- RETRIEVED: 모델을 사용하지 않은 검증된 번역 근거 검색 응답.
- SOURCE_GUIDANCE: 관련 출처 안내. 생성 실패 또는 본문 제공 제한 등으로 설명을 제공하지 못한 상태.
- SYNTHETIC_SCENARIO: 등록된 합성 사례의 고정 출처 설명. 모델 생성·임상 해석이 아니다.
- REFUSED / PERSONAL_INPUT_NOT_SUPPORTED / INSUFFICIENT_EVIDENCE: 임상 판단·개인 결과·근거 부족에 대한 제한된 안내.

5. 방금 완료한 QA HOLD 문구 수정

원인:
sourceGuidanceFromEvidence의 장애 안내와 sourceContextNote에 내부 QA HOLD/색인 PASS/검수 상태가 포함됐고, 환자 adapter가 이를 그대로 UI로 전달했다. 모델이 임의로 만든 문구가 아니다.

수정:
- patientPresentation에서 SOURCE_GUIDANCE 답변을 자연스러운 한국어로 교체.
- 원문 안내 답변: “이 질문에 대해 충분히 확인된 설명을 제공하기 어려워요. 아래 관련 원문 자료를 참고하고, 개인 검사 결과는 의료진과 확인해 주세요.”
- 출처 contextNote: “MedlinePlus 원문을 한국어로 옮긴 참고 자료입니다. 개인 검사 결과는 의료진과 확인해 주세요.”
- 기존 원래 source.contextNote는 source.reviewNote에 보존. reviewStatus도 유지. UI는 내부 reviewNote를 렌더링하지 않는다.
- 번역 SOURCE_GUIDANCE의 UI 상태 문구: “관련 원문 자료 안내 · 학교 발표용 건강 정보”.
- 생성 답변의 검증된 본문·출처는 그대로다.
- HOLD 자료에서 모델 실패 시 excerpt/listContexts를 제공하지 않는 기존 제한은 유지했다.
- shared 후보 코드를 일괄 수정하지 않았으므로 내부 후보 테스트의 QA HOLD 기대값은 남아 있을 수 있다. 이를 환자 화면 노출과 혼동하지 않는다.

중요: 위 staging 스크립트를 그대로 재실행하면 현재 파일에 이미 패치가 있어 anchor/equality 검사에서 실패할 수 있다. 범용 반복 배포 도구라고 가정하지 않는다. 현재 live 파일과 다음 수정 diff에 맞게 stage 로직을 먼저 준비·검증한다. initial RAG stage는 초기 연결 전 코드 가정을 가진다. 최신 이미지에 로컬 dirty tree 전체를 올리지 않는다.

SSH 키·known_hosts는 로컬 .ssh/highpass-capstone-cloud 아래 기존 설정을 코드가 사용한다. 키 내용·비밀번호·전체 환경변수·보호된 Compose 파일은 프롬프트나 로그에 복사하지 않는다. 기존 배포 권한과 인증 수단이 없는 다른 LLM은 로컬 수정·검증·배포 준비까지 수행하고 배포를 NOT VERIFIED로 기록한다.

9. 다음 개선의 우선순위

A. 재현과 평가
- AFP/초음파/CT/MRI 질문의 목적·준비·한계·비교·복합 의도를 분리한 평가 질문을 만들고 검색 및 응답 실패를 구분한다.
- 기존 test·holdout fixture를 먼저 읽어 중복 평가를 만들지 않는다.
- 답변의 관련성, 근거 정확성, 의도 충족, 내부 용어 비노출, 진단 금지, 지연·fallback 비율을 각각 기록한다.

B. 모델 실패 관측
- 현재 patient adapter가 모델 예외를 catch하고 fallback으로 전환하므로 실패 원인 구분이 어렵다.
- timeout/transport/relay busy/schema/claim validation failure를 내부 고정 코드로 구분하는 방법을 검토한다.
- 환자에게 stack trace나 내부 코드, 원 질문·원 응답을 노출·로그 저장하지 않는다.
- 최초 실패는 정확한 원인이 미확정이므로 cold start/CPU/동시성이라고 단정하지 않는다.

C. 검색과 답변 구성
- 검색 누락·잘못된 의도 선택을 먼저 해결한 뒤 답변 구조를 개선한다.
- 핵심 설명 → 필요한 주의사항 → 출처 순서로 간결하게 제공한다.
- 현재의 근거 문장 선택과 검증을 유지하면서 개선할 수 있는 부분부터 구현한다.
- 자유로운 요약을 추가하려면 근거 없는 주장·출처 불일치·수치 평가를 막는 별도 검증 및 회귀 평가가 선행돼야 한다.

D. 운영 안정성
- 기존 relay·SSH·Ollama의 시작·종료·동시성·지연을 점검한다.
- 공개 모델 포트, 새 유료 Azure 리소스, 모델 교체는 현재 범위를 자동으로 확대하지 않는다.
- 재배포 후 live checksum과 실제 모델 smoke를 모두 확인한다.

10. 다른 LLM에게 붙여 넣을 실행 프롬프트

너는 기존 하이패스 Platform의 건강도우미 RAG를 이어받는 시니어 풀스택 개발자다. 프로젝트를 새로 만들지 말고 현재 코드와 Azure 배포를 확인한 뒤 최소 범위로 개선해라.

작업 폴더는 C:\Users\user\Documents\New project이며 Azure 환자웹은 https://highpass-demo.japaneast.cloudapp.azure.com/hipass/ 이다. 먼저 docs/implementation/health-helper-llm-handoff-20261014.txt 전체와 AGENTS.md, REQUIREMENTS/ARCHITECTURE/SECURITY 및 관련 최신 구현 기록을 읽어라. 인수인계 이미지와 테스트 결과는 마지막 관측값이므로 실제 현재 상태와 구분해라.

내 목표는 학교 발표용 한국어 번역 RAG 건강도우미의 답변 품질과 안정성을 개선하는 것이다. 별도 검토자를 두지 않는다. QA HOLD 같은 내부 용어를 환자 답변으로 보여주지 마라. 이 표현 수정은 이미 배포됐으므로 다시 초기 상태로 만들거나 전체 검수 상태를 PASS로 바꾸지 마라. 이미 구현된 환자용 표현 분리와 내부 검증을 유지해라.

다음 순서로 실제 작업해라:
1) 현재 코드·API·검색·모델 연결·live 배포 기준선을 조사하고 확인된 사항/가정/불확실성을 구분해라.
2) AFP/초음파/CT/MRI 관련 질문을 재현해 검색 실패, 모델 실패, 근거 검증 실패, 답변 구성 문제를 나눠라. 최초 모델 호출 실패 후 재검증 통과 이력이 있으므로 간헐 실패를 우선 조사해라.
3) 가장 영향이 큰 재현 가능한 문제부터 최소 수정해라. 설명만 하지 말고 파일을 수정해라. 근거 검색 정확도와 질문 의도에 맞는 짧은 한국어 답변을 개선해라.
4) QA/HOLD/UNASSIGNED/색인 PASS 같은 상태는 내부 관측에만 남겨라. 실패 안내는 자연스럽게 표현하되 실제로 생성하지 않은 답변을 AI 생성으로 표시하지 마라.
5) 기존 단위·HTTP·환자 UI 회귀와 정상/장애/거절 검증을 실행하고 PASS/FAIL/NOT VERIFIED로 보고해라. 출력 문장은 검색 근거와 대응해야 한다.
6) 기존 Azure 배포 경로와 권한이 있으면 최신 live 이미지를 캡처하고 관련 파일만 반영한 후보를 검사한 뒤 배포·공개 파일 hash·실제 모델 smoke를 확인해라. 다른 작업의 dirty 파일과 live 변경을 보존해라. 권한이 없으면 검증 가능한 패치와 배포 절차를 제공하고 미배포를 명시해라.

필수 제약:
- 기존 Entra 환자 인증, 서버 PATIENT 역할 검사, 본문 override 차단, 감사, 시간 제한, rate limit을 유지해라.
- 원 질문·환자 수치·식별정보·개인 기록을 모델에 전달하거나 로그에 남기지 마라.
- 실환자 데이터·실제 임상 진단·처방은 구현하지 마라.
- 합성 HCC 고정 시나리오는 등록 환자와 카탈로그 범위에서만 동작하고, 임상 추론처럼 표시하지 마라.
- HOLD 자료의 장애 시 본문 제한 등 근거 검증을 제거해 답변률만 높이지 마라.
- 의료영상·동의·토큰·DB 구조를 관련 없이 변경하지 마라.
- 새 유료 리소스 생성, 공개 모델 포트, 인증 우회, 비밀정보 노출을 하지 마라.
- 사용자가 실제 로그인은 나중에 하기로 했으므로 이를 완료했다고 말하지 마라. 서비스 합성 principal 검증과 실제 로그인 HTTP/브라우저 검증을 구분해라.

완료 보고에는 수정 전 문제와 근거, 수정 파일, 관련 요구사항, 테스트 결과, Azure 반영 여부·주소·증적, 남은 문제와 미검증 사항을 포함해라. 문구 제거만으로 전체 답변 품질이 해결됐다고 주장하지 마라.
