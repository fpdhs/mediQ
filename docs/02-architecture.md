# 02 — 파이프라인 설계

## 전체 흐름

```
① 수집    HF daily_papers(JSON) + HN(points≥100) + Tier2 RSS + GeekNews
             ↓  SQLite 적재 (자연 키: arXiv ID / 정규화 URL)
② 중복    arXiv ID 매칭 → 제목 임베딩 유사도 0.85+ 묶기 → 대표 1건 선택
             ↓
③ 스코어  화제도 × 1차출처 확인 × 최근 중복 감점 → 상위 5건
             ↓
④ 초안    Claude API — 앵글 지정 + 1차 출처 링크 첨부
             ↓
⑤ 게이트  매일 아침 초안 5개 전달 → 사람이 2~3건 선택·수정   ← 자동화하지 않는 지점
             ↓
⑥ 발행    공식 Threads API (graph.threads.net)
```

①~③이 첫 구현 범위다. ④~⑥은 ①~③을 2주 돌려 소스 품질과 가중치를 검증한 뒤에 붙인다.

⑤의 전달 경로는 텔레그램 봇이나 마크다운 파일이면 충분하다. 여기에 웹 UI를 만들 필요 없다.

## ① 수집

`sources.yaml`을 단일 진실 원천으로 읽는다. 구현 시 걸리는 지점 세 개:

- **포맷 분기** — RSS는 `<item>`, Atom은 `<entry>`. GeekNews·Simon Willison·Lil'Log이 Atom이다.
  `<item>`만 찾는 파서는 이들에서 조용히 0건을 반환한다.
- **압축** — DeepMind 피드는 gzip으로 응답한다. Accept-Encoding 협상이 없으면 깨진 바이너리다.
- **JSON 소스** — HF daily_papers와 (스코프 외) CISA KEV는 RSS가 아니다. 별도 어댑터.

## ② 중복 제거

AI 뉴스에서 이게 사실상 전부다. 한 사건을 20개 매체가 쓴다. 3단으로 거른다.

1. **URL 정규화** — `utm_*`, `fbclid` 등 추적 파라미터 제거 후 비교
2. **자연 키** — arXiv ID(`paper.id`)가 있으면 그것으로 동일성 판정. 가장 정확하다
3. **제목 임베딩 유사도** — 코사인 0.85 이상이면 같은 사건으로 묶고, 그중 Tier가 낮은
   (= 1차 출처에 가까운) 항목 하나만 대표로 남긴다

3번이 없으면 "OpenAI 신모델 발표"가 하루에 여섯 번 큐에 쌓인다. 임계값 0.85는 시작값이고
실제 데이터로 조정할 대상이다.

## ③ 스코어링

```python
score = log(1 + hf_upvotes) * 2.0
      + log(1 + hn_points)  * 1.5
      + 1.5 if github_repo else 0          # 코드 공개 = 실용성
      + 2.0 if seen_in_tier2 else 0        # 1차 출처로 교차 확인됨
      - 3.0 if similar_posted_within_7d    # 최근 다룬 주제
```

`log`를 씌우는 이유는 upvote 500인 논문이 50인 논문보다 10배 중요하지는 않기 때문이다.

**가중치는 초기값일 뿐이다.** 2주 돌려보고 "상위 5건에 내가 올리고 싶은 게 들어 있나"를
기준으로 조정한다. 이 튜닝이 파이프라인 품질의 대부분을 결정한다.

## ④ 초안 — 발행 각도

단순 요약은 피해야 한다. AI 뉴스 요약 계정은 이미 포화 상태고, 같은 소스를 같은 방식으로
돌리는 계정이 수백 개다. 초안 생성 프롬프트에 앵글을 고정해 두는 편이 효과적이다.

| 앵글 | 내용 | 비고 |
|---|---|---|
| **이게 실제로 뭘 바꾸나** | 벤치마크 숫자 대신 개발자 워크플로 변화 | 범용 |
| **써봤다** | `githubRepo`가 있는 논문을 실제로 돌려본 후기 | 차별화 최상, 시간 소요 |
| **어제 X, 오늘 Y — 연결하면** | 개별 뉴스를 흐름으로 묶기 | 누적 DB 필요 |
| **과장된 부분** | 발표 수치와 실제 조건의 간극 | 신뢰 획득 |

세 번째가 자동화와 궁합이 가장 좋다. 수집을 몇 달 돌리면 남들이 못 쓰는 글이 나온다.
**이 프로젝트의 진짜 자산은 발행 기능이 아니라 누적된 DB다.**

## ⑤ 휴먼 게이트

`docs/04-decisions.md`의 ADR-002 참고. 요약하면 — 자동화가 먹는 부분은 수집·중복제거·
스코어링·초안 생성이고, 마지막 선택과 각도는 사람이 쥔다.

하루 목표 발행량은 **2~3건**이다. Threads API 상한은 24시간 250건이지만
([03-threads-api.md](03-threads-api.md)) 실질 제약은 API가 아니라 팔로워의 인내심이다.

## 저작권

요약 3~4줄 + 출처 명기 + 원문 링크를 벗어나지 않는다. 피드가 본문 전문을 주더라도
(국내 `gn_rss` 계열이 그렇다) 전재하지 않는다. 피드에 실린 이미지를 그대로 업로드하는 것도
피한다.

## 기술 선택

오케스트레이션은 **직접 코드 + cron**을 권한다. n8n으로도 가능하지만, ②의 3단 중복 제거가
노드로 표현하기 까다롭다 — 임베딩 유사도로 클러스터링한 뒤 Tier 기준으로 대표를 뽑는
로직은 코드가 훨씬 짧다.

검토했다가 택하지 않은 것들은 [ADR-003](04-decisions.md#adr-003-postiz-를-쓰지-않는다)에 있다.
