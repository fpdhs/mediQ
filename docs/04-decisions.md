# 04 — 결정 기록

조사 과정에서 내린 판단과 그 이유. 나중에 "왜 이렇게 했지"를 되짚거나 뒤집을 때 쓴다.

---

## ADR-001 — 스코프를 AI 트렌드로 좁힌다

**상태**: 채택 (2026-09-28)

처음 범위는 "AI 트렌드 + 보안 뉴스"였다. 조사 중 두 주제의 자동화 요구가 정반대라는 게
드러났다.

| | 보안뉴스 / CVE | AI 트렌드 |
|---|---|---|
| 핵심 가치 | 정확성 + 속도 | 해석 + 선별 |
| 중복 문제 | 적음 (CVE-ID로 식별) | 극심 (한 뉴스를 20곳이 씀) |
| LLM 요약 적합도 | 높음 (사실 나열형, 템플릿화 가능) | 낮음 (요약만 하면 스팸 취급) |
| 발행 방식 | 조건 충족 시 완전 자동 가능 | 사람 승인 필요 |

같은 파이프라인에 넣으면 둘 다 망한다. 분리하거나 하나를 버려야 했고, AI 트렌드를 택했다.

**결과적으로 자동화하기 쉬운 절반을 버린 셈이다.** 보안 라인은 CISA KEV처럼 이미
큐레이션된 소스가 있고 템플릿 발행이 가능했다. AI 트렌드만 남기면 전 과정에 판단이 필요하다.
이걸 알고 택했다.

보안 소스 검증 결과는 폐기하지 않고 `sources.yaml`의 `out_of_scope_security`와
[01-sources.md](01-sources.md#스코프-외--보안-뉴스-검증-결과-보존)에 보존했다. 되살릴 때
재조사가 필요 없다.

## ADR-002 — 완전 자동 발행을 하지 않는다

**상태**: 채택 (2026-09-28)

RSS → 요약 → 발행을 그대로 돌리면 3주 안에 조용해진다. 같은 소스를 같은 방식으로 돌리는
계정이 이미 수백 개다. AI 뉴스 요약 스레드는 포화 시장이다.

목표를 이렇게 재정의했다:

> 아침에 초안 5개가 준비되어 있고, 내가 2~3개 골라 손봐서 올린다.

자동화가 담당하는 것: 수집, 중복 제거, 스코어링, 초안 생성.
사람이 쥐는 것: 최종 선택과 각도.

이건 타협이 아니라 이 도메인에서 지속 가능한 유일한 형태다. 발행량이 목표가 되는 순간
품질이 떨어지고, 품질이 떨어지면 자동화를 유지할 이유가 없어진다.

## ADR-003 — Postiz를 쓰지 않는다

**상태**: 채택 (2026-09-28)

[Postiz](https://github.com/gitroomhq/postiz-app) (AGPL-3.0, 36.4k★)는 처음에 1순위
후보였다. Threads를 정식 지원하고, RSS 자동발행이 내장이고, Docker로 셀프호스팅된다.
소스가 3~4개고 그대로 흘려보내는 용도라면 코드 없이 끝난다.

**택하지 않은 이유**: 이 프로젝트에 필요한 건 발행이 아니라 선별이다.

- 소스가 15개 이상
- arXiv cs.LG 하나만 하루 수백 건 — 그대로 흘리면 계정이 죽는다
- 3단 중복 제거(URL 정규화 → arXiv ID → 임베딩 유사도)가 필수
- 스코어링과 휴먼 게이트가 핵심

Postiz의 RSS 자동발행은 "피드 → 그대로 게시"를 잘 하는 도구고, 우리가 필요한 건 그 앞단이다.
발행 자체는 공식 Threads API 직접 호출이 몇십 줄이므로 도구를 끼울 이득이 없다.

**뒤집을 조건**: 멀티 플랫폼(X, LinkedIn 등) 동시 발행이 필요해지면 재검토할 만하다.
그때는 선별 파이프라인의 출력을 Postiz에 넣는 구성이 된다.

## ADR-004 — n8n 대신 직접 코드

**상태**: 채택 (2026-09-28)

n8n에는 RSS → 멀티 플랫폼(Threads 포함) 발행 템플릿과 "RSS 없는 사이트를 AI로 스크랩·요약"
템플릿이 이미 있다. 소스 추가가 시각적으로 쉽다는 장점도 명확하다.

그런데 파이프라인 ②의 중복 제거가 노드로 표현하기 까다롭다. 제목을 임베딩해 코사인
유사도로 클러스터링하고, 각 클러스터에서 Tier가 가장 낮은 항목을 대표로 뽑는 로직은
코드로 쓰면 수십 줄이고 노드로 쓰면 지옥이다. 이 로직이 품질의 핵심이라 타협할 부분이 아니다.

**뒤집을 조건**: 중복 제거를 별도 서비스로 빼고 n8n이 그걸 HTTP로 호출하는 구성이라면
n8n의 장점만 취할 수 있다. 소스가 30개를 넘어가면 고려할 만하다.

## ADR-005 — 비공식 Threads 라이브러리를 쓰지 않는다

**상태**: 채택 (2026-09-28)

`Danie1/threads-api`, `iSarabjitDhiman/MetaThreads` 등 리버스 엔지니어링 계열은 계정 정지
위험이 있고 Meta가 내부 API를 바꾸면 예고 없이 깨진다. 공식 API가 무료이고 발행에 필요한
기능이 다 있으므로 쓸 이유가 없다. 상세는 [03-threads-api.md](03-threads-api.md).

## ADR-006 — HF Daily Papers를 선정의 중심축으로 삼는다

**상태**: 채택 (2026-09-28)

"무엇이 중요한가"를 기계가 판단하는 건 이 프로젝트에서 가장 어려운 문제였다. arXiv를 직접
긁으면 하루 수백 건이 쏟아지는데 제목·초록만으로 중요도를 매길 방법이 없다.

`https://huggingface.co/api/daily_papers`가 이걸 우회한다 — 사람이 이미 골라놓은 50건에
`upvotes`, `numComments`, `githubRepo`가 붙어 있다. **판단을 커뮤니티에 외주 주는 것**이
현재 최선의 해법이라고 봤다.

**한계와 뒤집을 조건**: 이 소스는 논문 편향이다. 제품 출시, 규제 동향, 업계 투자 같은
비논문 트렌드는 못 잡는다. 그래서 Tier 1에 Hacker News와 GeekNews를 함께 두고, Tier 2의
1차 출처로 교차 확인한다. 논문 외 트렌드 비중을 늘리려면 Tier 1 신호원을 추가해야 한다.
